# Стандарт: `Тест_к_теории.ipynb`

Actionable-инструкция для автора/агента. Файл лежит в `Урок_N_…_Теория/Тест_к_теории.ipynb` (занятие **N**, то же, что теория). UTF-8 (`encoding='utf-8'`).

Старый формат `{topic}_exercises.ipynb` **не создавать** — единственный артефакт проверки теории: `Тест_к_теории.ipynb`.

---

## 0. Сначала core, потом вопросы (обязательно)

Тест проверяет **самые важные базовые понимания** занятия, а не дополнительные пункты.

1. Прочитать теорию (цели в шапке, H2, чек-лист в конце).
2. Составить короткий список **core must-know** (5–12 пунктов): цель занятия + ключевые понятия, без которых нельзя идти на практику.
3. Каждый вопрос теста должен явно бить в один (или два связанных) пункт из этого списка.
4. **Запрет / сильное ограничение:** не включать optional, разделы со `*`, advanced, «на полях», экзотические edge-cases и концептуально второстепенные детали.
5. Разнообразие форматов (MCQ, matching, short answer, compute, image) **не оправдывает** уход во второстепенные темы: сначала покрытие core, потом выбор формата.

Если сомневаешься — выкинь вопрос про мелочь и замени вопросом про цель занятия / главный риск / главный протокол (train/val/test, метрика, утечка, главная модель урока).

## 1. Структура ноутбука

| Элемент | Правило |
|---------|---------|
| Имя файла | `Тест_к_теории.ipynb` |
| Шапка | `# Занятие N. Мини-тест: …` + 1–2 строки: короткая проверка теории; перечислить типы заданий |
| Число задач | обычно **10–12** (допустимо 8–15); лучше меньше и по core, чем много мелочей |
| Ячейка задачи | markdown с полями ниже; для compute/coding — markdown + **отдельная** code-ячейка |
| Metadata | `name`: `Тест_к_теории` |
| Student-facing | без мета-истории правок (см. `no-edit-history-in-lesson-text`) |

### Поля markdown-задачи (LMS-совместимый каркас)

```markdown
## K. Нейтральный заголовок без спойлера

**Тип:** выбор ответа | сопоставление | открытый ответ | вычисление / код | упорядочивание | верно/неверно | по картинке

**Задание.** …

**Варианты ответа:**          # для MCQ
**Варианты для сопоставления:** # для matching
**Формат ответа:** …          # для открытого / короткого ввода

**Правильный ответ:** …
```

Для **вычисление / код**: в markdown — условие и смысл; в code — пропуски `...`, данные/подсказки, `assert`, короткий `print("ok")`. Правильный ответ проверяется assert’ами (можно кратко продублировать ожидаемое в markdown для LMS).

## 2. Разнообразие типов (не только MCQ)

В одном тесте должны встречаться **несколько** типов. Ориентир микса (гибко, но без монотонности «все A–D»):

| Тип | Когда | Минимум по тесту |
|-----|--------|------------------|
| **выбор ответа** (MCQ, один верный) | понятия, выбор действия, интерпретация | 3–6 |
| **сопоставление** (matching) | роли train/val/test, термин↔смысл, метод↔ситуация | ≥1 |
| **открытый / короткий ввод** | число, слово, короткая фраза; проверяемый ответ | ≥1–2 |
| **вычисление / код** | небольшой расчёт или numpy/sklearn → понимание теории | ≥1–2 |
| **по картинке** | интерпретация графика/схемы с точки зрения теории | ≥1, если в теории есть ключевые графики |
| **упорядочивание** | порядок шагов пайплайна | по уместности |
| **верно/неверно** | умеренно (не больше 1–2); формулировка не трюковая | по уместности |

Не раздувать тест ради «закрыть все типы»: типы служат core, а не наоборот.

---

## 3. Дистракторы (MCQ)

- Неправильные варианты **визуально и по стилю** похожи на правильный: длина, тон, «разумность».
- Не короткие/глупые («потому что так надо»), не очевидно абсурдные.
- Лучшие дистракторы = **типичные ученические ошибки** из теории урока (утечка, путаница train/test, неверная метрика, «fit на всём»).
- Обычно **4** варианта A–D; один верный.

## 4. Заголовки без спойлеров

В `## K. …` **нельзя** подсказывать ответ.

| Плохо | Хорошо |
|-------|--------|
| `## 3. Test нельзя использовать для подбора k` | `## 3. Роль test при выборе гиперпараметра` |
| `## 5. Нужен StandardScaler для kNN` | `## 5. Масштабирование признаков для kNN` |

## 5. Compute / coding

- Небольшой расчёт **или** короткий код (numpy / sklearn), ведущий к ответу, который показывает понимание **теории урока**.
- Проверка: `assert` на результат (и при необходимости на промежуточные величины).
- **Запрещено как единственный смысл задачи:** тривиальная арифметика без ML-смысла; «просто `.fit().score()`» без интерпретации.
- Хорошие примеры: голосование соседей kNN; вклад признака в расстояние; ручной шаг градиента/остатка; чтение числа из confusion matrix / вероятности порога; эффект масштаба на норму.

---

## 6. Вопросы по картинкам

- Вставлять изображение **прямо в markdown** как  
  `![краткое описание](data:image/png;base64,...)`.
- **Не** ссылаться на отдельные файлы (`practice_images/…`, `../img/…`).
- Вопрос требует **интерпретации** графика/схемы в терминах теории (что растёт/падает, где переобучение, какой split честный), а не «какой цвет линия».
- Картинка должна иллюстрировать **core**-идею (validation curve, learning curve, границы kNN, дерево и т.п.), не декоративный advanced-кейс.

---

## 7. Стиль и проверяемость

- Аудитория ~**8 класс** / начинающий: без необъяснённого жаргона; англ. термин при первом появлении — по-русски.
- Ответы **проверяемы**: однозначный ключ для MCQ/matching/числа; для открытого — эталон 1–3 предложения + допустимые эквиваленты по смыслу.
- Согласованность с темой и сквозной моделью теории занятия **N**.
- Не дублировать полный пайплайн практики: тест = понимание, не 90-минутный проект.

- [ ] Заголовки без спойлеров ответа.
- [ ] Дистракторы сопоставимы по длине/стилю, похожи на типичные ошибки.
- [ ] UTF-8; в тексте для ученика нет истории правок.
- [ ] Шапка называет занятие **N**; ссылка на практику — **N+1**, если упоминается.
