# Generate presentation notebook

Исходные теории курса — **методические**: для учителя и для школьника, который повторяет материал или пропустил урок. Работать с ними учителю у доски во время урока неудобно.

Этот skill из методического ноутбука делает ноутбук для урока **`_presentation`**.

## Идейная рамка (не нарушать)

- сохраняем весь материал, который нужно демонстрировать (графики, формулы и т.п.);
- заменяем рассказ теории на вопросы для диалога, там где это уместно (нужно ли применять стандартизацию в knn? а в деревьях? в чем отличие?);
- после вопросов в отдельных ячейках ключевые выводы выделяем. То, что учитель проговаривает в процессе или обсуждает с учениками — убираем. Код пишем там, где нужно показать, как это выглядит в sklearn, например.

Методический ноутбук **не перезаписывать**. Presentation — отдельный артефакт рядом с теорией.

## Когда применять

- пользователь просит presentation / доску / `_presentation` / «ноутбук для урока»;
- явно назван skill `generate-presentation-notebook`;
- нужно сократить методическую теорию до сценария живого урока.

Не применять к практикам, тестам и `*_hand_solution.ipynb`.

## Вход и выход

| | |
|--|--|
| **Вход** | Методический ноутбук теории (`Урок_N_...Теория/*.ipynb`, не тест) |
| **Выход** | Тот же каталог, имя с суффиксом `_presentation` перед `.ipynb` |

Примеры имён:

- `Урок_31_Решающее_дерево.ipynb` → `Урок_31_Решающее_дерево_presentation.ipynb`
- `35_Градиентный_бустинг.ipynb` → `35_Градиентный_бустинг_presentation.ipynb`

Если файл уже есть — обновить его (или спросить, если пользователь просил только черновик).

## Роли двух ноутбуков

| Методическая теория | Presentation |
|---------------------|--------------|
| Полный рассказ, самоучитель | Каркас урока у доски |
| Длинные абзацы «почему» | Вопросы классу + короткий вывод |
| Повтор для пропустивших | Темп живого занятия |
| Все оговорки и края | Только то, что показывают и фиксируют |

Presentation **не** учебник и **не** конспект «всё словами». Это сценарий: спросить → показать → зафиксировать.

## Что оставлять

1. **Демонстрации:** графики, схемы, таблицы с числами из прогона, анимации/сравнения до–после.
2. **Формулы**, без которых нельзя говорить у доски (модель, loss, обновление, метрика).
3. **Минимальный код sklearn** (и numpy/pandas), когда цель — «как это выглядит в коде»: конструктор, `fit`/`predict`, ключевой параметр, 5–15 строк, не стену.
4. **Структуру урока:** те же крупные разделы `## N. …`, что в теории (номера не ломать — ссылки из практики/упражнений живые). Разделы `*` повышенной сложности — включать только если есть сильное демо; иначе одна строка «по желанию / в методичке».
5. **Сквозной датасет и `random_state`** — как в источнике, чтобы картинки совпали по смыслу.

## Что убирать

- Длинный повествовательный текст, который учитель и так скажет голосом.
- Повторы одной идеи разными словами.
- Абзацы «для самочтения» без демо и без вопроса.
- Блоки «Что видно» целиком как простыню — заменить вопросом («что бросается в глаза на графике?») и **коротким** выводом после ответа класса.
- Дубли markdown-таблица + тот же DataFrame без новой информации — одно из двух.
- Чек-лист «проверьте себя» в конце — по желанию свернуть в 3–5 устных вопросов, не копировать методичку.
- Ссылки «см. п. N» на соседние разделы — не засорять; нумерация разделов и так видна.

## Паттерн ячеек раздела

Не обязательно сначала все вопросы, потом все демо, потом выводы — это может **чередоваться как живой урок**.

Типичные ходы (комбинировать внутри раздела и между разделами):

```text
вопрос → демо → вопрос по картинке → вывод
демо → «что бросается в глаза?» → вывод
вопрос → вывод          (если код не нужен)
заголовок → демо → вывод  (если раздел чисто показательный)
```

Антипример жёсткого шаблона на весь ноутбук:

```text
## 1. … все вопросы
## 2. … все вопросы
… потом пачка кода …
… потом пачка выводов
```

Так урок не ведётся. Ритм — **локальный**: спросил → показал / обсудили → зафиксировали → следующий ход.

Правила:

- Вопрос и ответ на него **не** в одной ячейке: сначала пауза для класса, потом демо и/или вывод.
- Вывод — **отдельная** markdown-ячейка, визуально явная, например:

```markdown
> **Вывод.** Дереву масштабирование не нужно: оно сравнивает признак с порогом.
> kNN и линейным моделям — нужно: там работают расстояния и веса.
```

- Вывод ставят **после** того куска диалога/демо, который его готовит — не обязательно в конце всего раздела.
- В одном разделе может быть несколько коротких циклов «вопрос → демо → вывод», а не один большой блок каждого типа.
- Если раздел чисто демонстрационный — можно без вопросов: заголовок → код/график → вывод.
- Если раздел чисто понятийный — вопросы + вывод; не выдумывать бесполезный код.
- Не превращать каждый абзац теории в вопрос. Вопрос уместен, когда есть **выбор, сравнение, ошибка или интуиция**.

## Как писать вопросы

Хорошие вопросы для доски:

- сравнение моделей/приёмов: «нужно ли применять стандартизацию в kNN? а в деревьях? в чём отличие?»
- прогноз до демо: «если увеличить глубину дерева, train-ошибка упадёт. А validation?»
- чтение графика: «на какой кривой смотрим, чтобы выбрать `k`?»
- ловушка: «можно ли подобрать порог по test?»

Плохие:

- «Что такое переобучение?» с ожиданием абзаца из учебника;
- вопросы, ответа на которые нет в этом уроке;
- пять вопросов подряд без демо между ними.

Формат:

```markdown
**Обсудим:**

1. …
2. …
```

## Как писать выводы

- Одна мысль — один маркер; без новых терминов, которых не было в теории.
- Можно чуть короче методички, но **не искажать**.
- Не писать «учитель говорит…» — только содержание фиксации.
- Числа из прогона (accuracy, MAE) — только если они реально получаются в соседней code-ячейке.

## Шапка presentation

Первая ячейка — коротко, иначе чем методичка:

```markdown
# Занятие N. {Тема} — presentation

Ноутбук для работы **у доски**. Полный текст и самоучитель:
`{имя_методического_файла}`.

Вопросы — для диалога с классом. Блоки **Вывод** — то, что фиксируем после обсуждения.
```

Не копировать длинный список «к концу занятия вы сможете» из методички (или сократить до 3 пунктов максимум).

## Рабочий процесс агента

1. **Прочитать** методический ноутбук целиком (структура `## N.`, демо-код, ключевые формулы).
2. **Составить карту разделов:** для каждого H2 — (оставить демо / вопросы / убрать прозу / пропустить `*`).
3. **Собрать новый ipynb** с нуля (не патчить методичку); UTF-8; ячейки markdown/code как выше.
4. **Перенести код демо** из источника, упростить комментарии; убрать печать простыней, оставить график и 1–2 ключевых `print`.
5. **Прогнать** presentation (`nbclient` / аналог), убедиться: 0 traceback, графики на месте.
6. **Сверить** с рамкой: нет ли снова длинного рассказа; есть ли выводы отдельными ячейками; номера разделов стабильны.
7. Кратко отчитаться пользователю: путь файла, сколько разделов, что сознательно опущено.

Подробные before/after: [examples.md](examples.md).

## Ограничения курса

- Кодировка UTF-8; не портить кириллицу.
- Не использовать знак `§` в текстах; ссылки — **п.** / **пп.** только если без них нельзя.
- Не менять `plan.md` и не трогать практику/тест без запроса.
- Не коммитить, пока пользователь не попросил.
- API sklearn — актуальные параметры (как в методичке).
- Presentation не заменяет теорию в `status.md`, пока пользователь явно не решит иначе.

## Критерий готового файла

- [ ] Имя `*_presentation.ipynb` рядом с теорией
- [ ] Демо (графики/формулы/sklearn) на месте, ноутбук выполняется
- [ ] Рассказ заменён вопросами там, где уместен диалог
- [ ] Ключевые выводы — отдельные ячейки после вопросов/демо
- [ ] Убрано то, что учитель проговаривает или обсуждает вслух
- [ ] Номера `## N.` согласованы с методичкой
- [ ] Нет ощущения «второй методички»: текст заметно короче источника
